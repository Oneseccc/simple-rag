● Not hard at all — it's essentially a single environment variable change.
  Here's how it works:

  Switching between Groq and Ollama is just changing one line in .env:

  # Use Groq (default):
  LLM_PROVIDER=groq
  GROQ_API_KEY=gsk_your_free_key_here

  # Switch to Ollama (fully local):
  LLM_PROVIDER=ollama

  Then restart the stack. If using Ollama, you'd run docker compose --profile 
  local up to also start the Ollama container.

  In code, we'd have a single llm.py module with a provider abstraction — both
  Groq and Ollama expose OpenAI-compatible APIs, so the actual client code is
  nearly identical (just different base URL and model name). It's maybe ~15
  extra lines of code vs. supporting only one.

  The real benefit of supporting both:
  - Groq for daily use / demos — fast, high-quality 70B model, no RAM pressure
  - Ollama for "it works offline on a laptop" — fully satisfies the "no paid API
   key" requirement without any doubt
  - Shows good design (configurable, not hardcoded) — evaluators will notice
  this

  The docker-compose profiles feature means docker compose up starts only app +
  chromadb (Groq mode), while docker compose --profile local up additionally
  starts Ollama. No wasted resources either way.

  My recommendation: go with "support both." The effort is minimal and it's
  strictly better for the submission. Want me to proceed with that and the other
   questions?

     RAG Service Hackathon — Implementation Plan

     Context

     Build a containerized RAG service that answers questions about Anthropic
     Claude documentation, with rigorous evaluation. Scoring: Working System 25%
      / Eval 25% / AI Workflow 20% / Code Quality 15% / Docs 15%. Must run on
     16GB RAM, no paid APIs.

     Stack Decisions

     Component: Language
     Choice: Python 3.11 + FastAPI
     Rationale: Task preferred; async, great typing support
     ────────────────────────────────────────
     Component: LLM
     Choice: Groq free tier (default) + Ollama fallback
     Rationale: Configurable via LLM_PROVIDER env var. Groq: fast 70B quality.
       Ollama: fully offline with llama3.2:3b (faster on CPU than qwen)
     ────────────────────────────────────────
     Component: Embeddings
     Choice: all-MiniLM-L6-v2 via sentence-transformers
     Rationale: ~90MB, runs in-app, no extra service needed
     ────────────────────────────────────────
     Component: Vector Store
     Choice: ChromaDB (server mode, own container)
     Rationale: Simplest setup, good API, fits scale
     ────────────────────────────────────────
     Component: Chunking
     Choice: Markdown-aware recursive splitting
     Rationale: 2-stage: MarkdownHeaderTextSplitter →
       RecursiveCharacterTextSplitter. Configurable chunk_size/overlap
     ────────────────────────────────────────
     Component: Evaluation
     Choice: DeepEval with Groq LLM as judge
     Rationale: Cleaner API than RAGAS, supports all 5 required metrics
     ────────────────────────────────────────
     Component: Corpus
     Choice: Anthropic Claude docs (30-50 pages)
     Rationale: User's choice

     Bonus features: Web UI (plain HTML/JS) + Configurable chunking parameters
     Extra credit: Deferred — architecture supports adding agentic features
     later via src/agents/ module

     Verify: curl localhost:8080/health → 200 OK

     Phase 2: Ingestion Pipeline

     Goal: POST /ingest accepts a folder path, chunks documents, stores in
     ChromaDB

     Files to create:
     - src/core/chunker.py — Two-stage: MarkdownHeaderTextSplitter (split on
     #/##/###) → RecursiveCharacterTextSplitter (chunk_size=512, overlap=50).
     PDF via pymupdf4llm → markdown first. Chunk ID format:
     {filename}::{header_path}::chunk_{idx}
     - src/core/embedder.py — Singleton SentenceTransformer('all-MiniLM-L6-v2').
      Methods: embed_texts(list[str]) → list[list[float]], embed_query(str) →
     list[float]
     - src/core/vectorstore.py — ChromaDB HttpClient. Methods: add_documents(),
     query(), get_collection_stats(). Uses get_or_create_collection()
     - src/api/ingest.py — POST /ingest accepts {"folder_path": 
     "corpus/anthropic"} or file upload. Walks folder, loads files by extension,
      chunks, embeds, stores. Returns count + chunk IDs
     - src/models/schemas.py — IngestRequest, IngestResponse, QueryRequest,
     QueryResponse, Source, HealthResponse
     - config.yaml — chunk_size, chunk_overlap, headers_to_split_on (exposed as
     configurable bonus)

     Verify: Ingest one .md file → query ChromaDB directly → confirm chunks
     stored with metadata

     Phase 3: Query Pipeline (core RAG)

     Goal: POST /query returns answer with source citations and chunk IDs

     Files to create:
     - src/core/llm.py — Provider abstraction. GroqProvider uses groq SDK.
     OllamaProvider uses httpx to hit Ollama API. Both implement
     generate(prompt, system_prompt) → str. Factory function based on
     LLM_PROVIDER env var. Both support OpenAI-compatible chat format
     - src/core/rag.py — RAGPipeline class: (1) embed query, (2) retrieve top-k
     from ChromaDB, (3) build prompt with chunk IDs labeled in context, (4) call
      LLM, (5) format response with sources. Prompt template instructs LLM to
     cite [chunk_id] and say "I don't know" when context is insufficient
     - src/api/query.py — POST /query endpoint, validates input, calls
     RAGPipeline, returns QueryResponse

     Query response format:
     {
       "answer": "Claude supports up to 128 tools... 
     [prompt-caching.md::Overview::chunk_0]",
       "sources": [
         {"chunk_id": "...", "source_file": "...", "section": "...",

       "model": "llama-3.3-70b-versatile",
